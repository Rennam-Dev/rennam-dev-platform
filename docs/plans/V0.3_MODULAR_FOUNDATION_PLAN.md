# Plano técnico v0.3.0 — Fundação modular

> **Estado:** proposto; somente análise e planejamento.
>
> **Base analisada:** `5475e4e`, tag `v0.2.1`, readiness **B — pronta para
> evolução funcional, mas não para produção**.
>
> **Escopo de execução futura:** quatro tarefas pequenas, reversíveis e sem
> migration ou dependência nova. Este documento não autoriza implementação.

## 1. Decisão técnica

A v0.3.0 deve corrigir quatro pontos localizados da fundação existente:

1. tornar preventivo o teste que garante autenticação em toda rota
   administrativa;
2. consolidar a entrada do formulário de projetos e alinhá-la aos limites já
   existentes no model;
3. mover as operações ORM de escrita de projetos e tecnologias para o
   repository, sem criar um repository genérico;
4. tornar o service de projetos a única fronteira de `commit`/`rollback` e
   traduzir conflitos de persistência antes que alcancem a route.

Não há evidência para reescrever a arquitetura, criar uma camada de casos de
uso genérica, alterar models ou dividir agora `app/routes/admin.py`. O monólito
modular, a renderização SSR e os controles de segurança atuais permanecem
adequados.

São restrições de não regressão da milestone: monólito modular, FastAPI,
Jinja2/SSR, compatibilidade com HTMX, PostgreSQL, SQLAlchemy 2, Alembic,
autenticação por sessão, CSRF, Argon2, rate limiting, logging de autenticação,
security headers e o gate `make verify`.

**Migration na v0.3: NÃO.** As quatro tarefas tratam organização, validação de
entrada, persistência e testes. Nenhuma exige alterar tabela, coluna, índice,
constraint ou dado existente. As invariantes de banco registradas como dívida
P2 continuam fora desta milestone; misturá-las à fundação modular ampliaria o
escopo e obrigaria uma migration sem necessidade para iniciar o Blog CMS.

**Mudança no roadmap: NÃO.** O plano apenas detalha a “Fundação modular” já
prevista em `docs/ROADMAP.md`. Blog CMS, workflow editorial, SEO avançado,
internacionalização e Labs permanecem nas versões já aprovadas.

## 3. Fluxo real atual

### 3.1 Fluxo público de leitura

```text
HTTP GET
  → route FastAPI em app/routes/public.py
  → dependency get_db quando há leitura persistida
  → repository de projetos
  → SELECT SQLAlchemy + Project/Technology
  → route monta contexto
  → TemplateResponse Jinja2 SSR
  → HTML com Markdown sanitizado quando aplicável
```

Esse fluxo já está correto para home, listagem e detalhe de projetos:

- as routes tratam parâmetros, status 404, contexto e resposta;
- `app/repositories/projects.py` contém as queries e aplica o escopo público
  `visibility == "published"`;
- os models permanecem restritos ao mapeamento ORM;
- templates cuidam da apresentação, e o filtro Markdown centralizado em
  `app/web.py` sanitiza a saída.

Não há schema nem service nesse caminho porque ele é somente leitura e não
possui regra de negócio além do escopo expresso pela consulta. Adicionar essas
camadas seria indireção sem benefício atual.

A única query SQLAlchemy diretamente em uma route pública é `SELECT 1` em
`app/routes/public.py:124-127`, usada pelo endpoint de health. Ela é uma sonda
de infraestrutura, não persistência de domínio. Separar liveness/readiness e
tratar falha como 503 continuam dívida operacional P2, não tarefa da v0.3.

### 3.2 Fluxo administrativo de criação

```text
POST /admin/projetos/novo
  → require_admin como dependency FastAPI
  → request.form()
  → validate_csrf()
  → read_project_form()
      → novo request.form()
      → ProjectForm / Pydantic
  → route consulta repository para unicidade do slug
  → project_service.create_project()
      → instancia Project
      → consulta/adiciona Technology diretamente com SQLAlchemy
      → adiciona Project
      → commit + refresh
  → route captura IntegrityError e executa rollback
  → RedirectResponse ou template 422
```

Pontos corretos:

- autenticação e CSRF são verificados antes da mutação;
- Pydantic é a validação server-side autoritativa;
- o service recebe dados validados, não `Request` ou `Response`;
- o redirect pós-sucesso evita reenvio do formulário;
- conflito conhecido retorna o formulário, sem expor erro de banco.

Vazamentos comprovados:

- a regra de unicidade é orquestrada na route
  (`app/routes/admin.py:248-250`), embora a constraint do banco ainda precise
  resolver corridas;
- `app/services/projects.py:40-45` consulta e adiciona `Technology`, e
  `app/services/projects.py:53` adiciona `Project`, apesar de persistência ser
  responsabilidade documental do repository;
- o service faz `commit` (`app/services/projects.py:54`), mas a route faz
  `rollback` (`app/routes/admin.py:257-259`);
- a route conhece `IntegrityError`, uma exceção de infraestrutura;
- o mesmo formulário é lido duas vezes e sua lista de campos é repetida entre
  `app/routes/admin.py:124-155` e `app/schemas/project.py:7-25`.

### 3.3 Fluxo administrativo de atualização

```text
POST /admin/projetos/{id}/editar
  → require_admin
  → repository busca Project
  → request.form() + validate_csrf()
  → read_project_form() + ProjectForm
  → project_service.update_project()
      → regra de slug imutável
      → atualização dos campos
      → consulta/sincronização de tecnologias
      → commit + refresh
  → route traduz ProjectSlugImmutableError
  → route captura IntegrityError e executa rollback
  → RedirectResponse ou template 422
```

A regra de slug está no local correto: o service a aplica antes de qualquer
mutação (`app/services/projects.py:59-69`) e lança uma exception sem semântica
HTTP. O vazamento é novamente a divisão da transação e o conhecimento de
`IntegrityError` pela route.

Há ainda uma inconsistência de ordem: a atualização busca o projeto antes de
validar CSRF (`app/routes/admin.py:307-312`), enquanto criação e exclusão
validam o token primeiro. A tarefa de formulário deve uniformizar a ordem para
`auth → ler formulário uma vez → CSRF → acesso ao recurso → validação → caso de
uso`, sem enfraquecer qualquer controle.

### 3.4 Exclusão bloqueada e login

O bloqueio de hard delete está corretamente separado:

- `delete_project()` sempre lança `ProjectDeletionDisabledError` no service;
- a route traduz a regra para HTTP 409 e registra a tentativa;
- não existe `db.delete()` nesse fluxo;
- autenticação e CSRF continuam obrigatórios.

O login também está suficientemente modular para o escopo atual:

- a route observa IP, lê formulário e monta respostas HTTP;
- `LoginRateLimiter` é independente de FastAPI e tem relógio injetável;
- credenciais, sessão e CSRF estão centralizados em `app/core/security.py`;
- o logging sanitizado possui configuração própria e testes.

Não há justificativa para mover ou redesenhar esse fluxo na v0.3.

| Queries SQLAlchemy em routes | **Adequado com uma exceção operacional** | Não há query de Project/Technology nas routes. Apenas `SELECT 1` do health em `app/routes/public.py:124-127`; manter fora da v0.3. |
| Regra de negócio em routes | **Vazamento localizado** | Checagem de slug duplicado em `app/routes/admin.py:248-250`; mover para o caso de uso de criação. |

| `add`/queries de escrita | **Fora da fronteira documentada** | `app/services/projects.py:40-45` e `:53` acessam o ORM diretamente; mover para funções específicas do repository. |
| Validação duplicada | **Parcialmente justificada** | A repetição HTML + Pydantic deve permanecer como UX + segurança. A repetição da extração/coerção de campos na route e no schema deve ser reduzida. |
| Limites schema/model | **Lacuna concreta** | Os três `HttpUrl` não limitam 500 caracteres, enquanto o model usa `String(500)` em `app/models/project.py:47-49`. PostgreSQL pode rejeitar entrada aceita pelo schema. |

| Imports entre camadas | **Quase adequado** | `IntegrityError` na route e `select` no service são os desvios relevantes. O type hint `Session` nas routes para `Depends(get_db)` é aceitável. |
| Helpers sem responsabilidade clara | **Nenhum bloqueador** | Contexto, IP observado, auditoria, resposta limitada e valores de formulário têm responsabilidades identificáveis. Não extrair por estética. |
| Services acoplados a HTTP | **Não** | Nenhum service importa `Request`, `Response`, `HTTPException` ou templates. Preservar. |
| Repositories com regra de negócio | **Não** | Filtros de publicação são contratos de consulta; não há transição de estado ou decisão editorial nos repositories. |
| Funções grandes | **Não** | `admin.py` tem 376 linhas, mas seus handlers e helpers são curtos e separados; o maior risco vem da fronteira transacional, não do tamanho isolado. |
| HTTP misturado com domínio | **Parcial** | Exceptions de slug e exclusão estão saudáveis; `IntegrityError` chegando à route é a mistura a remover. |
| Duplicação que piora com Blog/Journal | **Sim, localizada** | Copiar o mapeamento de formulário, checagem de conflito e rollback da route para Article/Category/Tag multiplicaria o padrão inconsistente. |

## 5. `app/routes/admin.py` não deve ser dividido agora

**Recomendação: NÃO dividir `app/routes/admin.py` na v0.3.**

O módulo contém nove endpoints em dois blocos reconhecíveis — autenticação e
projetos — e helpers pequenos. Não há query de domínio direta, mutação de model
na route ou função monolítica que justifique mover endpoints. Uma divisão agora
tocaria imports, registro de router e testes de segurança sem resolver o
problema central de transação e persistência.

O ganho concreto para v0.4 vem de não adicionar Article ao mesmo arquivo. O
Blog CMS deve nascer em um router próprio, por exemplo `admin_articles.py`,
quando seus casos de uso existirem. Só então haverá evidência para decidir se o
router atual deve ser renomeado para projetos ou se um agregador administrativo
é útil. Essa decisão deve acompanhar código real de Article, não antecipá-lo.

Extrair agora um router de auth, um router de projetos e um agregador produziria
movimentação ampla, risco de regressão em `require_admin`/CSRF e pouco benefício
para os nove endpoints atuais. O teste preventivo proposto na tarefa M3.1 é uma
proteção mais valiosa e muito menor.

## 6. Fronteira transacional recomendada

A política deve ser explícita e continuar baseada em `Session` do SQLAlchemy,
sem Unit of Work genérico ou framework externo.

| Operação | Responsável | Regra |
|---|---|---|
| `add` | Repository específico | Anexar `Project` e `Technology` à sessão somente em funções de persistência com nomes de domínio. |
| `flush` | Repository específico | Materializar IDs e constraints quando o service solicitar a persistência; nunca encerrar a transação. |
| `commit` | Service do caso de uso | Exatamente um commit ao final de cada comando bem-sucedido (`create`/`update`). |
| `rollback` | Service do caso de uso | Reverter qualquer falha ocorrida após o início da mutação, antes de traduzir ou propagar a exception. |
| `close` | Dependency `get_db` | Continuar responsável somente pelo ciclo de vida da sessão; não fazer commit implícito por request. |
| Nenhuma das quatro | Route | A route valida HTTP/CSRF, chama o caso de uso e converte exceptions conhecidas em resposta. |

Consequências práticas:

- repositories não fazem `commit` ou `rollback`;
- services podem continuar recebendo `Session` explicitamente; esconder a
  sessão atrás de DI ou Unit of Work seria arquitetura excessiva;
- routes deixam de importar `IntegrityError` e de chamar `rollback`;
- o service captura `IntegrityError`, faz rollback e lança uma exception
  específica, como `ProjectConflictError`;
- exceptions inesperadas de infraestrutura não devem ser mascaradas como erro
  de validação. Elas são revertidas e propagadas para o tratamento 500.

Essa política prepara a criação atômica futura de `Article` com `Category` e
`Tag`: ou todo o agregado é persistido, ou nada é confirmado.

## 7. Tratamento de erros recomendado

O desenho atual já separa corretamente dois tipos de erro:

- `ValidationError` nasce no schema e a route o transforma em formulário 422;
- `ProjectSlugImmutableError` e `ProjectDeletionDisabledError` nascem no
  service e a route os transforma em 422/409.

A única correção necessária para v0.3 é impedir que a exception de
persistência atravesse a fronteira:

```text
Pydantic ValidationError
  → route preserva valores e responde 422

ProjectSlugImmutableError / ProjectDeletionDisabledError
  → route mapeia para o status e template já existentes

SQLAlchemy IntegrityError
  → service faz rollback
  → service lança ProjectConflictError sem detalhe interno
  → route responde 422 com mensagem controlada

Erro inesperado de infraestrutura
  → service faz rollback quando houver mutação ativa
  → erro propaga para 500/logging
```

Não criar uma hierarquia global de exceptions, middleware de domínio ou
envelope de erro nesta milestone. Handlers SSR globais, headers em 500 e a
separação liveness/readiness continuam importantes antes de produção, mas são
dívida P2 distinta da Fundação modular.

`require_admin` e `validate_csrf` podem continuar lançando `HTTPException`, pois
são dependências da fronteira web, não regras de domínio. Movê-las de
`app/core/security.py` para um novo pacote apenas mudaria o endereço do código.

## 8. Avaliação dos schemas

`ProjectForm` está suficientemente proporcional ao produto atual:

- é específico do recurso, não uma abstração genérica;
- define campos obrigatórios, limites de texto, slug, status e visibilidade;
- normaliza whitespace;
- converte URLs validadas em strings para o model;
- não depende de FastAPI, `Request`, `Response` ou SQLAlchemy.

Não há motivo para separar já `ProjectCreate`, `ProjectUpdate`, DTO de domínio e
view model. A imutabilidade do slug é corretamente uma regra do service, e os
campos de criação/edição ainda são praticamente iguais.

Dois ajustes pequenos são necessários:

1. concentrar no schema de projeto a construção a partir dos dados do
   formulário, incluindo checkbox e URLs vazias, para a route não repetir o
   contrato de campos;
2. limitar as URLs a 500 caracteres, alinhando a validação ao model e à
   migration existentes.

Os atributos HTML `minlength`, `maxlength`, `pattern` e `type=url` devem
continuar nos templates para UX, enquanto Pydantic permanece autoritativo no
servidor. Isso é defesa em camadas, não duplicação a eliminar.

Article, Category e Tag devem receber schemas próprios na v0.4. Não criar na
v0.3 um `BaseContentForm`, enum editorial compartilhado ou schema genérico para
um domínio ainda inexistente.

## 9. Tarefas da v0.3.0

### M3.1 — Tornar preventivo o contrato de autenticação administrativa

**Objetivo**

Fazer o teste partir do inventário completo das rotas sob `/admin` e exigir
`require_admin` em todas, exceto `GET /admin/login` e `POST /admin/login`
explicitamente públicas.

**Problema atual que comprova a necessidade**

`tests/test_admin.py:130-141` monta o conjunto somente com rotas que já possuem
a dependência e o compara a uma lista estática. Uma nova rota sem
`require_admin` não apareceria em nenhum dos dois lados e poderia manter o teste
verde. A auditoria mais recente classifica isso como dívida P3 a resolver na
próxima ampliação da superfície administrativa; a v0.4 é exatamente esse
gatilho.

**Mudança proposta e benefício concreto**

- Inventariar primeiro todas as combinações método/path do router admin.
- Declarar somente os dois endpoints de login como públicos.
- Para cada rota restante, afirmar a presença de `require_admin`.
- Na v0.4, uma nova route de Article sem proteção falhará imediatamente.
- Na v0.5, novos comandos de preview/publicação/workflow continuarão negados
  por padrão.

**Arquivos prováveis**

- `tests/test_admin.py`

**Comportamento que NÃO deve mudar**

- Login continua público.
- Dashboard, logout e todas as rotas de projetos continuam protegidos.
- Redirect 303 para `/admin/login`, sessão e CSRF permanecem iguais.

**Testes necessários**

- teste de inventário preventivo;
- matriz sem sessão para todas as rotas atuais;
- `make verify` no gate da tarefa.

**Risco**

Baixo. O principal risco é classificar incorretamente uma futura rota pública.
A mitigação é manter uma allowlist explícita, mínima e revisável apenas para o
login.

**Se não fizermos agora**

O primeiro endpoint administrativo do Blog poderá ser adicionado sem
`require_admin` e sem falha no teste que hoje aparenta garantir cobertura.

**Dependências**

Nenhuma. Deve ser a primeira tarefa para proteger as alterações seguintes.

**Reversibilidade**

Reverter somente o teste de inventário; não há mudança de runtime, banco ou
dados.

**Commit sugerido**

`test: make admin authorization inventory preventive`

### M3.2 — Consolidar o contrato de entrada do formulário de projetos

**Objetivo**

Ler cada formulário mutável uma única vez, validar CSRF antes de buscar o
recurso e concentrar em `ProjectForm` a coerção dos campos HTTP já existentes.

**Problema atual que comprova a necessidade**

- criação e atualização chamam `request.form()` e depois
  `read_project_form(request)`, que chama `request.form()` novamente
  (`app/routes/admin.py:124-155`, `:245-247` e `:310-312`);
- a route repete todos os campos e defaults já declarados em
  `app/schemas/project.py:7-25`;
- atualização consulta o projeto antes de validar CSRF;
- `repo_url`, `demo_url` e `cover_image_url` aceitam pelo schema URLs maiores
  que os `String(500)` do model.

**Mudança proposta e benefício concreto**

- Adicionar ao schema de projeto uma factory específica para um mapping de
  formulário; não criar base class genérica.
- Fazer a route ler o form uma vez, validar CSRF e passar o mapping ao schema.
- Preservar na route apenas a conversão de `ValidationError` em mensagens e
  resposta 422.
- Alinhar os três limites de URL a 500 sem mudar o banco.
- Na v0.4, Article terá um único contrato de coerção para Markdown, categoria,
  tags, draft e preview, em vez de repetir listas de campos em handlers.
- Na v0.5, a inclusão de estados editoriais ocorrerá no schema do recurso, sem
  espalhar parsing por routes.

**Arquivos prováveis**

- `app/schemas/project.py`
- `app/routes/admin.py`
- novo `tests/test_project_schemas.py`
- `tests/test_admin.py`

**Comportamento que NÃO deve mudar**

- Formulários válidos criam e editam os mesmos dados.
- Checkbox `featured`, URLs vazias, stripping de whitespace e preservação de
  valores após erro continuam iguais.
- HTML SSR, status 422, mensagens Pydantic, CSRF e redirects permanecem.
- A única mudança intencional é uma URL maior que 500 caracteres falhar como
  validação controlada, em vez de chegar inválida ao PostgreSQL.

**Testes necessários**

- unitários para mapping do formulário, checkbox, URLs vazias e whitespace;
- URL com 500 caracteres aceita quando válida e acima do limite rejeitada;
- status/visibility/slug inválidos continuam 422;
- teste provando uma única leitura do form ou, preferencialmente, API do helper
  que recebe o mapping já lido;
- POST de atualização com CSRF inválido não chama o repository;
- regressões de criação e atualização administrativas;
- `make verify`.

**Risco**

Baixo a médio. Coerção incorreta pode perder valor digitado ou alterar uma
mensagem. Os testes devem comparar payload válido, valores redisplayados e
status atuais.

**Se não fizermos agora**

Article/Category/Tag tenderão a copiar o mesmo mapping manual, e entradas que o
schema aceita mas o banco rejeita continuarão produzindo falhas de persistência
evitáveis.

**Dependências**

Depende apenas de M3.1 como guardrail de execução; não depende de mudança no
repository.

**Reversibilidade**

Reverter factory, uso na route e testes no mesmo commit. Não há transformação
de dados nem alteração de schema.

**Commit sugerido**

`refactor: consolidate project form input validation`

### M3.3 — Completar a fronteira de escrita do repository de projetos

**Objetivo**

Concentrar no repository as queries e operações ORM de persistência de
`Project` e `Technology`, mantendo parsing, slug e associação como regras do
service.

**Problema atual que comprova a necessidade**

`app/repositories/projects.py` contém somente leituras, enquanto
`app/services/projects.py:4-5`, `:40-45` e `:53` importa `select`, consulta
`Technology` e executa `db.add`. Isso contradiz a responsabilidade aprovada de
repositories para consultas e persistência e seria copiado para Article, Tag e
Category.

**Mudança proposta e benefício concreto**

- Adicionar funções específicas para localizar tecnologia por slug, adicionar
  tecnologia, adicionar projeto e fazer o flush necessário.
- Manter funções simples sobre `Session`; não criar classe base, protocol,
  repository genérico ou DI externa.
- Manter `parse_technologies`, `slugify` e a decisão sobre a relação no service.
- Repository nunca faz `commit` ou `rollback`.
- Na v0.4, repositories de Article/Category/Tag terão um padrão mínimo e
  explícito para leitura/escrita.
- Na v0.5, queries de workflow e persistência de transições poderão evoluir por
  recurso sem um framework genérico difícil de desfazer.

**Arquivos prováveis**

- `app/repositories/projects.py`
- `app/services/projects.py`
- novo `tests/test_project_repository.py` ou testes de integração equivalentes

**Comportamento que NÃO deve mudar**

- Criação, edição, sincronização e deduplicação case-insensitive de tecnologias
  permanecem iguais.
- Ordenação e filtros públicos permanecem iguais.
- O commit continua temporariamente no service e o rollback na route até M3.4;
  M3.3 deve ser isoladamente executável e reversível.
- Nenhum model, constraint ou migration muda.

**Testes necessários**

- localizar tecnologia existente por slug;
- persistir tecnologia nova e projeto na mesma sessão;
- sincronizar lista sem duplicar nomes equivalentes;
- garantir que funções do repository não chamam `commit`/`rollback`;
- regressões públicas e administrativas;
- `make verify`.

**Risco**

Médio-baixo. Alterar o momento de `flush` pode antecipar uma constraint. O teste
de integração deve confirmar o mesmo resultado final e que a transação ainda
não é encerrada pelo repository.

**Se não fizermos agora**

O service de Article provavelmente repetirá queries e `add` diretos, deixando a
fronteira documental ainda mais difícil de consolidar depois de Category e Tag.

**Dependências**

M3.1 concluída. É pré-requisito de M3.4.

**Reversibilidade**

Recolocar as chamadas ORM atuais no service e remover as funções de escrita do
repository. Como o formato persistido não muda, não há rollback de dados.

**Commit sugerido**

`refactor: move project persistence into repository`

### M3.4 — Centralizar transação e conflitos no service de projetos

**Objetivo**

Fazer cada comando de projeto possuir uma única unidade transacional no
service, mantendo a route livre de operações de transação e exceptions do
SQLAlchemy.

**Problema atual que comprova a necessidade**

- `create_project()` e `update_project()` fazem commit em
  `app/services/projects.py:50-71`;
- os handlers capturam `IntegrityError` e fazem rollback em
  `app/routes/admin.py:257-259` e `:322-324`;
- a route consulta previamente a unicidade do slug em
  `app/routes/admin.py:248-250`;
- uma falha entre mutação e tratamento exige conhecer duas camadas para provar
  atomicidade.

**Mudança proposta e benefício concreto**

- Mover a checagem de slug existente para `create_project()`, usando o
  repository.
- Fazer create/update chamar as funções de escrita/flush da M3.3.
- Executar exatamente um `commit` no fim do caso de uso.
- Em `IntegrityError`, executar rollback e lançar `ProjectConflictError` com
  mensagem controlada; em outra falha após mutação, rollback e re-raise.
- Antes do write, rejeitar nome de tecnologia cujo slug normalizado seja vazio
  ou colida com outro nome do mesmo formulário. Manter essa regra específica de
  projetos; Category/Tag definirão suas próprias regras quando existirem.
- Fazer a route mapear somente exceptions do service para 422/409.
- Não criar Unit of Work, decorator transacional ou exceção base global.
- Na v0.4, criar Article + relações será uma operação atômica e conflitos de
  slug/tag não vazarão SQLAlchemy para HTTP.
- Na v0.5, transições como draft → published ou scheduled → published poderão
  validar regra e persistir relações em um único commit, sem estado parcial.

**Arquivos prováveis**

- `app/services/projects.py`
- `app/repositories/projects.py`
- `app/routes/admin.py`
- `tests/test_admin.py`
- novo `tests/test_project_services.py`
- `docs/ARCHITECTURE.md`, apenas para registrar a política final de transação

**Comportamento que NÃO deve mudar**

- Slug continua imutável após criação.
- Hard delete continua bloqueado.
- Slug duplicado continua retornando 422 com mensagem controlada.
- Tecnologias válidas continuam sendo normalizadas e associadas como hoje; os
  casos vazios/colidentes passam intencionalmente a retornar 422 antes do banco.
- Sucesso continua redirecionando com 303 e `saved=1`.
- Nenhuma atualização parcial é persistida em falha.
- Auth, sessão, Argon2, CSRF, rate limit, logging e templates permanecem.

**Testes necessários**

- criação e atualização fazem um único commit;
- conflito de slug antes do write retorna exception do service;
- tecnologia com slug vazio ou colisão de normalização falha antes de `add` e
  sem mutação parcial;
- `IntegrityError` no flush/commit provoca rollback e
  `ProjectConflictError` sem detalhe interno;
- erro inesperado após mutação provoca rollback e é repropagado;
- slug imutável não altera nenhum outro campo;
- route não importa `IntegrityError` nem chama `rollback`;
- fluxo HTTP mantém 422/409/303 atuais;
- integração PostgreSQL no `make verify` e gate completo.

**Risco**

Médio. Fronteira transacional é sensível a regressão de atomicidade e a
exceptions durante flush/commit. A mitigação é implementar após M3.3, cobrir o
service diretamente e manter um único commit por comando.

**Se não fizermos agora**

Article com Category e Tag herdará commits/rollbacks divididos entre handler e
service, aumentando o risco de publicação parcial e duplicando tratamento de
conflito em cada route.

**Dependências**

Depende de M3.3. Deve ser a última alteração comportamental da v0.3.

**Reversibilidade**

Reverter service, mapeamento da route e testes em conjunto restaura a fronteira
anterior. Não há migration ou conversão de dados a desfazer.

**Commit sugerido**

`refactor: centralize project transaction boundary`

## 10. Ordem de execução e dependências

```text
M3.1 guardrail de auth
  ↓
M3.2 contrato de formulário
  ↓
M3.3 escrita no repository
  ↓
M3.4 transação e errors no service
  ↓
gate final make verify
```

M3.2 e M3.3 são tecnicamente independentes, mas a ordem sequencial reduz
conflitos e mantém cada diff pequeno. M3.4 depende obrigatoriamente da fronteira
de persistência de M3.3.

Cada tarefa deve ser um commit isolado apenas quando houver autorização
explícita para implementar e publicar. Este trabalho de planejamento não cria
nenhum commit.

## 11. Partes que NÃO devem ser refatoradas na v0.3

Esta seção é deliberadamente obrigatória: preservar código suficiente bom é
parte do plano.

### `app/routes/admin.py` como router único atual

Não dividir pelos motivos da seção 5. Criar o router de Article apenas quando a
v0.4 começar; não mover endpoints atuais preventivamente.

### Dependências de auth e `app/core/security.py`

`require_admin`, sessão, CSRF, Argon2 e os helpers de login/logout estão
centralizados e cobertos. Embora `require_admin` seja HTTP-aware, isso é
apropriado para uma dependency FastAPI. Um novo pacote `dependencies/` não
resolveria problema atual.

### Rate limiting e logging de autenticação

R1–R3 foram confirmadas. `LoginRateLimiter` é pequeno, bounded, thread-safe e
independente de HTTP; o logger sanitizado é idempotente e emite para stdout. Não
reabrir essas remediações durante uma refatoração de projetos.

### `app/main.py` e middlewares

A app factory pequena preserva TrustedHost, session cookie, headers, CSP, HSTS
condicional e fechamento de OpenAPI em production. Settings/engine globais têm
limitações conhecidas, mas não bloqueiam o CMS e mexer nisso ampliaria o risco
sem benefício para as quatro tarefas.

### Repositories públicos de projetos

As funções `list_published`, `list_featured`, `get_by_slug`, `get_by_id` e
`list_technologies` são explícitas, legíveis e mantêm rascunhos fora do público.
Não criar repository genérico nem trocar ORM models por DTOs para leitura SSR.

### Exceptions de domínio já existentes

`ProjectSlugImmutableError` e `ProjectDeletionDisabledError` estão no service e
não conhecem HTTP. Preservar esse desenho; adicionar apenas a exception de
conflito necessária.

### Models e migration inicial

Model e migration estão coerentes no escopo atual. CHECK constraints,
server-side defaults e outras invariantes de produção exigiriam uma migration e
pertencem à dívida P2. Não misturar essa remediação à v0.3.

### Sanitização Markdown e templates SSR

O filtro Markdown com allowlist e o autoescape Jinja devem permanecer. Não
introduzir editor, upload, SPA ou rendering client-side. O loader atual do blog
em arquivos é simples e será substituído/evoluído por casos reais na v0.4;
refatorá-lo ou adicionar cache agora seria trabalho descartável ou não medido.

### Infraestrutura de testes segura

A guarda do banco, o PostgreSQL descartável, o ciclo Alembic e `make verify`
foram estabilizados. As tarefas v0.3 apenas adicionam cobertura; não redesenham
fixtures, Compose ou locks.

## 13. Critérios objetivos de conclusão da v0.3.0

A milestone estará concluída somente quando:

1. M3.1–M3.4 forem implementadas e revisadas em diffs isolados;
2. o teste de auth partir de todas as rotas admin e admitir como públicas apenas
   as duas rotas de login;
3. cada POST de projeto ler o formulário uma vez e validar CSRF antes do acesso
   ao recurso/mutação;
4. `ProjectForm` rejeitar URLs acima do limite atual de 500 caracteres;
5. nomes de tecnologia com slug vazio ou colisão de normalização serem negados
   antes da persistência;
6. queries, `add` e `flush` de Project/Technology estiverem no repository;
7. repositories não executarem `commit` ou `rollback`;
8. routes de projetos não importarem `IntegrityError` nem chamarem `commit`,
   `rollback`, `add` ou `flush`;
9. create/update fizerem no máximo um commit no service e rollback em toda falha
   posterior ao início da mutação;
10. conflito de persistência chegar à route apenas como exception controlada do
   service;
11. services continuarem sem `Request`, `Response`, templates ou status HTTP;
12. os comportamentos preservados de auth, CSRF, sessão, Argon2, rate limit,
    logging, headers, SSR, rascunhos, slug e hard delete passarem sem regressão;
13. testes unitários, integração PostgreSQL, rotas e segurança passarem;
14. `make verify` passar integralmente, incluindo Ruff e ciclo Alembic;
15. `alembic check` não indicar drift e nenhuma migration nova existir;
16. nenhuma dependência nova existir;
17. documentação registrar a política transacional sem alterar a ordem do
    roadmap;
18. `git diff --check` passar e o diff final não conter v0.4+ nem alterações
    alheias.

A readiness ao final continua **B — pronta para evolução funcional, mas não
para produção**. A v0.3 não encerra os requisitos operacionais P2 de deploy,
backup/restore, observabilidade, liveness/readiness, erro 500 ou invariantes de
banco.

## 15. Resposta de readiness para iniciar v0.4

**Após executar este plano, a base estará preparada para iniciar v0.4 — Blog
CMS? SIM.**

Justificativa: a expansão administrativa terá negação por padrão verificável,
um contrato de formulário por recurso, persistência concentrada em
repositories e uma fronteira transacional/erro única no service. Esses são os
quatro pontos atuais que, se copiados, piorariam materialmente com Article,
Category e Tag.

“Preparada para iniciar” não significa que Blog CMS ou produção estarão
prontos. A v0.4 ainda deverá criar seus models e migrations próprios, definir
Article como default-private, garantir que draft/preview não entrem em
listagens/sitemap e testar publicação. Esses trabalhos pertencem corretamente à
v0.4. Os requisitos operacionais P2 continuarão impedindo classificação de
produção.
